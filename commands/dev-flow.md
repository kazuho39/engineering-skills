# Dev Flow

`specs/<feature>/` に **人間が `spec-driven-development` スキルで作成済み** の `specification.md` / `design.md`（と、`design-class-design.md`・`design-test-plan.md` などの分離文書）を入力として受け取り、実装 → レビュー → QA を自動で通すオーケストレーターコマンド。

このコマンド自身は仕様策定を行わない。仕様書・設計書がまだ無い場合は `spec-driven-development` スキルの使用を案内して終了する。

## プロジェクト設計ハブ（差し込み口）

プロジェクト固有の事情は `project-design-hub` スキルに集約する。このコマンドは、そのスキルが**あれば**起動して回答に従い、**なければ**下表の既定で進む。

**起動のタイミング**: 起動前チェックの開始時に一度だけ起動し、得た内容を各ステップで使う。

| 場面 | ハブに確認すること | ハブがないときの既定 |
|------|-------------------|--------------------|
| テストの実行コマンド | 全体テスト・絞り込み実行のコマンド（実行環境を含む） | プロジェクトのテスト設定（`package.json`、`composer.json`、`Makefile` など）から推定し、ユーザーに確認する |
| 実装の手順・規約 | 実装順、使う設計スキル、コーディング規約 | **テストファースト**（後述）で、契約に沿って進める |
| レビューの観点 | 観点ごとに使うスキル・チェック基準 | 設計・アーキテクチャ、セキュリティ、テスト、パフォーマンスの4観点 |
| ルール昇格 | レビュー指摘を再発防止ルールへ昇格するスキル | ステップ4を省略する |

ハブの指示は、プロジェクトの規約として扱う。ただし、このコマンドの安全上のルール（ユーザー確認が必要な点、成果物の出力先をリポジトリ内に限ること）や、ユーザーのチャット上の指示と矛盾する場合は、ユーザーに確認する。

## サブエージェント

各ステップは `Agent` ツールで、`developer` / `reviewer` / `qa` の名前のサブエージェント（`subagent_type`）を起動して行う。これらはプロジェクトのエージェント定義として用意しておく（プロジェクト固有の規約を反映してよい）。

定義が見つからない場合は、起動せずにユーザーへ「エージェント定義が必要です。engineering-skills の `agents/` にある汎用版を、プロジェクトのエージェント定義の置き場にコピーしてください」と案内して終了する。

サブエージェントは会話コンテキストを引き継がないため、必要な情報はすべてプロンプトに含める（後述の「コンテキスト受け渡しルール」）。

## 起動前チェック

0. 引数 `$ARGUMENTS` を解釈する
   - 対象ディレクトリ（`specs/` で始まるパス）: 省略可
   - `--checkpoint=manual|auto|skip`: 骨組みチェックポイントのモード（ステップ1b）。省略時は `manual`。それ以外の値は受け付けず、ユーザーに正しい値を案内して終了する
1. ユーザーから対象ディレクトリ（例: `specs/2026-07-19_product-search/`）を確認する。指定がなければ `specs/` 配下の最新ディレクトリを候補として提示し、ユーザーに確認する
2. 対象ディレクトリに `specification.md` と `design.md` が存在するか確認する
   - 存在しない場合: 「先に `spec-driven-development` スキルで仕様書・設計書を作成してください」と案内して終了する
3. 分離文書（`design-class-design.md`、`design-test-plan.md`、`design-adr.md`、`design-open-questions.md` など）の有無を確認し、あるものはパスを控える
4. 成果物の出力規約をユーザーに明示する: `review.md` / `test-report.md` は同じ `specs/<feature>/` 配下に作成される

## フロー全体

```
[入力] specification.md / design.md（+ 分離文書。人間が作成済み）
    ↓
1a. developer 起動（フェーズA）→ 骨組み（クラス・シグネチャ、本体は未実装）＋テストを作成 → Red 確認
    ↓
1b. 骨組みチェックポイント（設計整合性・テストの2観点）
    ├ manual: 骨組みとテストをユーザーに提示し、承認を待つ（既定）
    ├ auto  : reviewer を軽量モードで起動。must ありなら developer（フェーズA）に差し戻し
    └ skip  : 省略
    ↓ must なし／承認
1c. developer 起動（フェーズB）→ 実装 → Green 確認
    ↓
2. reviewer 起動 → review.md 作成
    ↓ 🔴 must あり
    └→ developer に差し戻し → 修正 → reviewer 再実行（最大3往復）
    ↓ 🔴 must 解消 / 元々なし
3. qa 起動 → 全体テスト実行 → test-report.md 作成
    ↓ 失敗あり
    └→ developer に差し戻し → 修正 → qa 再実行（最大3往復）
    ↓ 全件成功
4. （ハブがルール昇格スキルを示す場合）review.md の指摘から昇格候補を確認（情報提示のみ）
    ↓
5. 最終サマリを提示し、コミット/PR作成に進むかユーザーに確認
```

### テストファーストの進め方

developer は次の順で進める。ハブが実装順を示す場合はそれに従うが、**テストを実装より先に書き、失敗（Red）を確認する**点と、**フェーズA の後で一度止まる**点は変えない。

**フェーズA（骨組み＋テスト）**

1. 型・インターフェース・契約（`design-class-design.md`）を確定させる
2. 新規クラスとメソッドを作る。**シグネチャ（引数・戻り値の型）まで定義し、本体は「未実装であること」を明示する**（例外を投げるなど。ダミー値を返さない。Red が偶然 Green になるのを防ぐため）
3. `design-test-plan.md` のとおりにテストを書く
4. テストを実行し、**未実装による失敗**であることを確認する（Red）。書き間違い（構文エラーなど）による失敗なら、テストを直す

**骨組みチェックポイント**（ステップ1b）

**フェーズB（実装）**

5. 実装する
6. 担当スコープのテストを実行し、成功する（Green）まで実装を直す。テストの期待値を緩めて通さない。全体の回帰確認は qa の担当

フェーズB でテストの変更が必要になった場合（設計の誤りなど）は、テストを直す理由を完了報告に明記する。設計書の更新が必要なら、設計書を直して変更履歴を残す。

## 各ステップの実施方法

### ステップ1a: developer 起動（フェーズA）

プロンプトには以下を明示的に含める:

- `specification.md` / `design.md` のフルパスと要点（何を作るか、スコープ）
- 分離文書のフルパス。読む順は `design.md` の冒頭（開発概要・変更の有無）→ `design-class-design.md`（作るクラス）→ `design-test-plan.md`（作るテスト）→ 必要に応じて `design.md` の本編・`design-adr.md`・`design-open-questions.md`
- プロジェクトルートのパス
- 実装対象範囲（設計書の一部だけを実装する場合はその範囲を明記）
- ハブから得た、実装の手順・規約・テスト実行コマンド

- 今回は**フェーズA（骨組み＋テスト作成、Red 確認まで）**であり、実装はしないこと

developer が `BLOCKED: ...` 形式で応答した場合、原因をユーザーに提示し、回答を待ってから再実行する。

### ステップ1b: 骨組みチェックポイント

モードは引数 `--checkpoint` の値とし、指定がなければ `manual` とする（ハブでは変更しない）。

**manual**（既定）: フェーズA の完了報告をもとに、次の形式で**ユーザーに提示して止まり**、承認を待つ。長くしすぎず、1画面に収める。

```markdown
## 🛑 骨組みレビューのお願い（実装前）

骨組みとテストを作りました。実装はまだ始めていません。
下の3点だけ確認して、「承認」か「修正指示」を返してください。

### 作ったもの
- 骨組み（型だけ、本体は未実装）: N ファイル
- テスト: M ファイル / K ケース
- Red の確認: K 件中 K 件が「未実装」で失敗（想定どおり）／想定外の失敗が X 件（理由を併記）

### 確認してほしいこと（優先度順）
1. **テストの期待値は仕様どおりか**（一番大事）
   見る所: <完了報告の「人間に見てほしいテスト」を列挙>
   ここが間違っていると、実装もその方向に引っ張られます。
2. **骨組みの型は設計書の契約と一致しているか**
   見る所: `design-class-design.md` の <該当クラス> と <骨組みのファイル>
   確認: 引数・戻り値の型、メソッド名、例外の種類
3. **設計書のテストが抜けていないか**
   設計書にあるのにテストに無いもの: <自動チェックの結果。なければ「なし」>
   判定順・境界値・非破壊性のような、設計書が明示している所を特に見てください。

### 自動チェックの結果
- 本体がダミー値を返しているメソッド: <なし／一覧>
- 判定順・境界値・非破壊性に対応するテストの漏れ: <なし／一覧>

### 見なくてよいもの
Feature（HTTP 経由）の細かい観点や画面側のテストは、実装後のレビューと QA で確認します。

### 返答
- 「承認」→ 実装に進みます
- 「修正指示」→ 修正して、もう一度ここで止まります
```

- 「作ったもの」と「自動チェックの結果」は、developer の完了報告から転記する。報告に無い項目は、オーケストレーターが推測で埋めず、developer にフェーズA の再実行（追記）を依頼する。
- 修正指示があれば developer をフェーズA で再起動し、再提示する

**auto**: reviewer を**骨組みレビュー（軽量モード）**で起動する。プロンプトには、フェーズA の完了報告（作成・変更したファイル、Red 確認の結果）、`design-class-design.md`・`design-test-plan.md` のパス、モードが骨組みレビューであることを含める。
- 🔴 must が 0件 → ステップ1c へ
- 1件以上 → developer をフェーズA で再起動して修正させ、再レビューする（最大3往復。超えたらユーザーに判断を仰ぐ）

**skip**: ステップ1c へ進む。

### ステップ1c: developer 起動（フェーズB）

ステップ1a と同じ情報に加え、フェーズA の完了報告とチェックポイントでの指摘・指示を含める。「骨組みとテストは確認済み。実装して Green にすること」と明示する。

### ステップ2: reviewer 起動

プロンプトに含めること:

- レビュー対象の変更ファイル一覧（developer の完了報告から）
- `design.md`（と `design-class-design.md`）のパス（設計との整合性確認用）
- `review.md` の出力先パス（`specs/<feature>/review.md`）
- 初回か再レビューか
- ハブから得た、レビュー観点ごとのスキル・チェック基準

reviewer の完了報告を確認する:

- 🔴 must が **0件** → ステップ3へ進む
- 🔴 must が **1件以上** → 差し戻しループへ（下記）

### 差し戻しループ（reviewer → developer）

1. developer を再度起動する。プロンプトに以下を明示的に含める:
   - `review.md` のパス
   - 🔴 must 指摘の全文（指摘内容・ファイル:行・修正案）
   - 前回の変更ファイル一覧
2. developer の完了報告を受けて、reviewer を再実行（`review.md` のパスを渡し、再レビューであることを明示）
3. 🔴 must が解消されるまで 1〜2 を繰り返す。**3往復しても解消しない場合はループを止め、未解消の指摘とこれまでの経緯をユーザーに提示して判断を仰ぐ**

### ステップ3: qa 起動

プロンプトに含めること:

- 対象ディレクトリ（`test-report.md` の出力先）
- 今回のスコープに関連するテストファイル・対象領域
- 初回か再実行か
- ハブから得た、テスト実行コマンド

qa の完了報告を確認する:

- ✅ 全件成功 → ステップ4へ進む
- 🔴 失敗あり → 差し戻しループへ（下記）

### 差し戻しループ（qa → developer）

1. developer を再度起動する。プロンプトに以下を明示的に含める:
   - `test-report.md` のパス
   - 失敗したテストの全文（テスト名・失敗理由・スタックトレース）
2. developer の完了報告を受けて、qa を再実行
3. 全件成功するまで 1〜2 を繰り返す。**3往復しても解消しない場合はループを止め、未解消の失敗とこれまでの経緯をユーザーに提示して判断を仰ぐ**

### ステップ4: ルール昇格提案（ハブが示す場合のみ・情報提示のみ）

ハブがレビュー指摘の昇格用スキルを示していれば、`review.md` の指摘一覧を渡し、汎用的なルールへ昇格すべき指摘がないか確認する。示されていなければこのステップを省略する。

このステップはファイルを直接編集しない。ユーザーの承認を得てから対象ファイルへの追記・新規作成を行う。

### ステップ5: 最終サマリ

以下を提示して終了する。コミット自体は行わない。

```markdown
## Dev Flow 完了

### 変更ファイル一覧
- <path>

### 成果物
- レビュー結果: specs/<feature>/review.md（ステータス: ✅ 承認）
- テスト結果: specs/<feature>/test-report.md（ステータス: ✅ 全件成功）

### 残っている任意対応（🟡 should / 🟢 nits）
- <指摘>（対応は任意）

### 次のアクション
このままコミット/PR作成に進みますか？
```

## コンテキスト受け渡しルール

各サブエージェント呼び出しは会話コンテキストを共有しないため、呼び出しごとに以下を **省略せず明示的に** プロンプトへ含めること:

- 利用者の元の要求（何を実装したいか）
- プロジェクトルートのパス
- 対象ディレクトリ（`specs/<feature>/`）と、分離文書のパス
- 前段のペルソナの成果物パス・完了報告の内容
- 差し戻しの場合: 差し戻し元・指摘の全文・対象ファイル
- ドキュメントの命名規則（`review.md` / `test-report.md`）
- ハブから得た情報（テスト実行コマンド、実装の規約、レビュー観点）

## 人間チェックポイント

このフロー内でユーザーに確認を求めるのは以下のみ:

- 対象ディレクトリが曖昧なとき（起動前チェック）
- テスト実行コマンドが分からないとき
- 骨組みチェックポイントが `manual` のとき（ステップ1b）
- 骨組みレビューが3往復しても解消しないとき
- developer が `BLOCKED` を返したとき
- 差し戻しループが3往復しても解消しないとき
- ルール昇格提案の適用可否（ステップ4）
- フロー完了後、コミット/PR作成に進むかどうか（ステップ5）

それ以外（developer → reviewer → qa の正常系、および差し戻しループ）はノンストップで自動実行する。
