# domain-understanding（ドメイン知識を理解するための文書テンプレート）

ドメイン知識を整理し、設計や実装の前提としてそろえるための、文書の雛形です。事業やシステムに依存せず、コピーして `{...}` を埋めて使います。`templates/` 配下なので、コピーして初めて使われます。

## 作る順番と、各文書の用途

| 順 | 文書 | 用途 | この順にする理由 |
|---|---|---|---|
| 1 | [ステークホルダーとビジネス全体像](ステークホルダーとビジネス全体像.md) | 事業の目的・提供価値・収益の仕組みと、関わる人（利用者・運営・外部）を整理する。システムが事業の中で担う範囲と、担わない範囲を明らかにする | 以降の判断の拠り所になる |
| 2 | [業務フロー](業務フロー.md) | 業務の手順を、担当者ごとに分岐・例外を含めて書き出す。システム化する操作の粒度を決める入力になる。迷った点もここで拾う | 実際に何が行われるかを、テキストで出す。イベント一覧の代わりにもなる |
| 3 | [ユビキタス言語集](ユビキタス言語集.md) | 業務で使う言葉の定義をそろえ、同義語や使わない言葉を明示する。関係者とAIが同じ意味で話すための土台で、コードの命名にも直結する | 業務フローを書くと用語が自然に集まる。同時に育てる |
| 4 | [概念モデル図](概念モデル図.md) | 業務の概念とその関係を、技術詳細を除いて描く。エンティティ・値オブジェクト・集約の候補を見つける入力になる | 1〜3 から導く。最初の版は仮のモデルとして描く |
| 並行 | [ビジネスルール一覧](ビジネスルール一覧.md) | 業務上の制約・計算・判定をIDつきで並べ、根拠を残す。不変条件や例外の洗い出しと、ルール同士の矛盾の発見に使う | 業務フローの分岐・例外から、見つけたものを足していく |

## 使い方

1. 使うプロジェクトの文書置き場に、必要なファイルをコピーする
2. ファイル名と見出しの `{事業・システム名}` を置き換え、`{...}` の空欄を埋める
3. 表の行は、コピーして増やす。使わない章は削ってよい

```bash
mkdir -p <プロジェクト>/docs/domain
cp engineering-skills/templates/domain-understanding/*.md <プロジェクト>/docs/domain/
rm <プロジェクト>/docs/domain/README.md   # この説明は不要なら削除
```

## 進めるときのコツ

- 図や表を先に整えようとせず、業務の流れを書きながら、用語とルールを拾っていく
- 決めきれないことは止まらずに「疑問」や「要確認」として残し、未解決事項の文書にまとめる
- 概念モデル図は、ルールが固まる前は仮のものとして扱い、ルール一覧が育った段階で見直す
- 各ファイルの冒頭と各章の先頭に、書く内容の説明がある。消さずに残しておくと、書き手が変わっても読み方が伝わる
