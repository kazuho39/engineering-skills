# DDD クラス設計支援

DDD（ドメイン駆動設計）に沿って、値オブジェクト・エンティティ・Repository を設計・実装するスキル。
このスキルは単体で完結する。プロジェクトにレイヤー構成や命名の規約があればそれに従い、なければ本書の既定に従う。実装例は PHP で、他の言語では読み替える。

## このスキルを使用する場合

- 値オブジェクト・エンティティ・Repository を新規設計・実装するとき
- レイヤー間の依存関係を正しく設計したいとき
- ドメインモデルと永続化の境界（ORM との変換など）を整理したいとき

## 前提条件

- 設計対象のドメイン概念（何を表現したいか）
- 対象が値なのかエンティティなのかの整理

---

## レイヤーと依存方向

役割ごとに3つの層に分ける。

| 層 | 役割 | 置くもの |
|---|---|---|
| ドメイン層 | ビジネスルールのみ。外部ライブラリや永続化の知識を持たない | 値オブジェクト、エンティティ、ドメインサービス、Repository インターフェース |
| アプリケーション層 | ユースケース（処理の流れ）の組み立て | ユースケース、DTO |
| インフラ層 | 外部依存（DB・外部 API・ファイル）の実装 | Repository 実装、ORM モデル、変換処理 |

```
ドメイン ← アプリケーション ← インフラ
```

- **ドメイン層**は他のどの層にも依存しない
- **アプリケーション層**はドメイン層のみに依存する
- **インフラ層**はドメイン層・アプリケーション層に依存してよい
- **インフラ層からドメイン層への逆依存は作らない**（ドメインが永続化の都合に引きずられるため）

依存方向を機械的に検査できる仕組みがあれば使う（PHP なら Deptrac など）。ディレクトリ名や namespace の付け方はプロジェクトの規約に従う。

## ステップバイステップワークフロー

### 値オブジェクトを設計する

1. **参照**: [Value Object 設計ガイド](references/value-object.md)
2. 不変条件（バリデーションルール）を定義する
3. 不変（変更不可）なクラスとして実装する
4. 値の同一性を比較するメソッド（`equals()` など）を用意する

### エンティティを設計する

1. **参照**: [Entity 設計ガイド](references/entity.md)
2. 識別子（ID）を持つか確認する
3. ライフサイクルを考慮した状態遷移を定義する
4. 値オブジェクトを積極的に活用する

### Repository を設計する

1. **参照**: [Repository パターンガイド](references/repository-pattern.md)
2. ドメイン層にインターフェースを定義する
3. インフラ層に実装を作成する（永続化手段ごとに実装を分ける）
4. 実装クラスの差し替えは依存性注入で行う
