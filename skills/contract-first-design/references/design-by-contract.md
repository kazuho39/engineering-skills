# 契約による設計（Design by Contract）

「呼び出し側の不安（どんな結果が返る？）」と「呼ばれる側の不安（正しい値を渡してくれる？）」を、契約を明示して解消する設計手法（B. メイヤー、1986年）。

※ コード例は PHP。他の言語では読み替える。

## 3つの要素

| 要素 | 内容 | 責任を負う側 |
|---|---|---|
| 事前条件 | 呼び出す前に成り立っているべき条件 | 呼び出し側 |
| 事後条件 | 処理後に保証される結果（戻り値） | 呼び出される側 |
| 不変条件 | インスタンスが生きている間、常に満たす条件 | 呼び出される側 |

- 事前条件・事後条件 → メソッド実行後の正しい結果を保証できる
- 不変条件 → 不正値を防止できる
- 3条件が明確ならブラックボックステストを書ける。契約に基づくテストが通っていれば、その部分のレビューを省力化できる

## 事前条件を守る

- 「どういうデータが渡されるか」を明確にするため、プリミティブ型ではなく**ドメイン型**を使う
- 値単体で検証できない条件は、メソッド内の**ガード節**で検証する
- ガード節は、呼び出し側で保証すべき条件が破られたことを呼び出し側に知らせる役割も持つ

```php
final readonly class Quantity
{
    public function __construct(public int $value)
    {
        if ($value < 1 || $value > 99) {
            throw new \InvalidArgumentException("数量は1〜99: {$value}");
        }
    }
}
```

コンストラクタが唯一の入口なので、不正な `Quantity` は存在し得ない。受け取る側は範囲チェックが不要になる。

```php
public function addItem(Product $product, Quantity $quantity): self
{
    // 事前条件①: 状態に依存（VOでは表現できない）
    if ($this->isCheckedOut()) {
        throw new \DomainException('購入手続き後は商品を追加できない');
    }
    // 事前条件②: 引数と状態の組み合わせ
    if (!$product->isOnSale()) {
        throw new \DomainException('販売停止中の商品');
    }
    if ($this->totalQuantity() + $quantity->value > 99) {
        throw new \DomainException('カート内の合計が上限を超える');
    }

    // ここから先は事前条件が成立している前提
    return new self([...$this->items, new CartItem($product, $quantity)]);
}
```

※ 例では標準の例外を使っているが、プロジェクトに専用の例外を定める規約があればそれに従う。

## PHP で型を補強する手段

※ この節のコードは PHP の例。他の言語では、同等の仕組み（型宣言、列挙型、不変な型など）に読み替える。

| 手段 | 例 |
|---|---|
| 型宣言 | `int`, `string`, `?User`（null を許すか明示） |
| `declare(strict_types=1)` | `"5"` が `int` に暗黙変換されるのを防ぐ |
| Enum（8.1+） | `enum Status: string { case Draft = 'draft'; }` |
| `readonly`（8.1+/8.2+） | 生成後の変更を禁止し、不変条件を守る |
| 名前付き引数 | `new Money(amount: 100, currency: Currency::JPY)` |
| PHPDoc | `@param positive-int $n` を書き、PHPStan 等で静的検査 |

## 事後条件を守る

- 戻り値の保証は**型**で表す
- 戻り値をユーザー定義型にして「不正な結果を作れない」ようにする
- 事後条件は**テストで確かめる**（最重要）
- 変更のたびに新しいオブジェクトを返す設計は [immutable-design.md](immutable-design.md) を参照

## 信頼できるコードを AI に実装させる手順

1. 契約による設計でクラスの仕様を設計する
2. 副作用を隔離し、隔離したうえで純粋関数を作る
3. クラス仕様をテストでカバーする（契約に基づいてテストを実装する）

3条件が明確なら、先にテストを書き、それが通るように実装させられる。

## 契約からテストを導く

| 契約 | テスト |
|---|---|
| 事前条件 | 違反入力で例外になる（境界値: 下限-1 / 下限 / 上限 / 上限+1） |
| 事後条件 | 正常入力で戻り値が保証どおり |
| 不変条件 | 操作前後で条件が保たれる。不正値でインスタンスを作れない |
