# 契約ファースト設計

実装に入る前に、クラス・メソッドの**仕様を契約として明文化**し、**副作用を隔離**してから型とテストに落とすスキル。
「中身を読まないと正しい結果が分からないコード」を減らし、AI に実装させても信頼できる状態にすることが目的。

このスキルは単体で完結する。プロジェクトに配置・例外・テストの規約があればそれに従い、なければ各手順に書いた**既定**に従う。

## このスキルを使用する場合

- 新しい値オブジェクト / エンティティ / ユースケース / ドメインサービスを設計するとき
- 既存メソッドの仕様が曖昧で、何を保証するか決めたいとき
- 実装前に「何を保証するクラスにするか」を相談されたとき

## ワークフロー

設計では、**ステップ1〜5の成果物を順にユーザーへ提示**してから実装へ進む。契約表（ステップ3）がないまま実装に進まない。

### 1. 責務と配置の確認

- 設計対象が値（値オブジェクト）・状態遷移を持つもの（エンティティ）・処理の流れ（ユースケース）のどれかを決める
- 配置先はプロジェクトのレイヤー規約があればそれに従う
- **既定**: 次の3つの役割に分けて配置する
  - 純粋ロジックを持つ部分（値オブジェクト、エンティティ、ドメインサービス）
  - 副作用を持つ薄い部分（Repository、Mailer、Clock など）
  - 両者を呼ぶ順に並べるだけの部分（ユースケース）

### 2. 副作用の仕分け

処理を次の2つに分ける。

- **純粋な計算**: 同じ入力なら常に同じ出力。外部状態を読まず、書かない
- **副作用**: DB・メール・API・ファイル・ログ・現在時刻や乱数の取得・環境変数・自分や引数の状態書き換え

方針:

- 副作用は Repository / Mailer / Clock などの**薄いクラスに隔離**し、そこに副作用の操作以外のロジックを書かない
- 業務ロジックは純粋なメソッドに寄せる。ユースケースは「純粋な計算を呼ぶ → 副作用クラスを呼ぶ」の順に並べるだけにする
- 時刻・乱数・ID採番は引数または注入で受け取り、純粋ロジックの中で直接呼ばない
- 副作用を持つメソッドは動詞で名前を付け（`save` / `send` / `register`）、「計算」の名前で副作用を隠さない

→ 詳細は [references/side-effects.md](references/side-effects.md)

### 3. 契約の明文化（契約表）

メソッドごとに次の表を作る。

| メソッド | 事前条件（呼び出し側の責任） | 事後条件（戻り値の保証） | 不変条件 | 副作用 |
|---|---|---|---|---|
| `Cart::addItem` | 購入手続き前 / 商品が販売中 / 合計99個以下 | 商品を追加した新しい `Cart` を返す | 合計数量は常に99以下 | なし（純粋） |

- 事前条件: 呼び出す前に成り立っているべき条件
- 事後条件: 処理後に保証する結果（戻り値）
- 不変条件: インスタンスが生きている間、常に満たす条件
- 副作用: 「なし（純粋）」または何が起きるかを明記する

→ 詳細は [references/design-by-contract.md](references/design-by-contract.md)

### 4. 型への落とし込み

| 契約 | 表現方法 |
|---|---|
| 値単体で決まる事前条件 | 値オブジェクト / 列挙型のコンストラクタ検証（プリミティブ型を引数・戻り値に使わない） |
| 状態や引数の組み合わせに依存する事前条件 | メソッド冒頭のガード節（契約違反の例外を投げる） |
| 事後条件 | 戻り値の型をドメインの型にして、不正な結果を作れなくする |
| 不変条件 | 不変（変更不可）にする / コンストラクタを唯一の入口にする / 状態遷移メソッドで検証 |

- 言語に型の厳密化の仕組みがあれば有効にする（PHP なら `declare(strict_types=1)`）
- 例外は契約違反として扱う。例外の型や変換の規約がプロジェクトにあれば従う。**既定**: 契約違反は専用の例外型で表し、呼び出し側が通常の失敗と区別できるようにする

### 5. イミュータブル設計の判断

- **値オブジェクト**: 完全イミュータブル。変更が必要なら新しいインスタンスを返す（`withXxx` / `add` など）
- **エンティティ**: 状態遷移は許容するが、遷移メソッドごとに事前条件（今の状態から遷移できるか）を契約表に書き、不変条件を遷移後も満たすことを保証する
- 引数の参照渡し変更・静的 / グローバル状態の書き換えはしない

→ 詳細は [references/immutable-design.md](references/immutable-design.md)

### 6. テスト仕様 → 実装

1. 契約表から**ブラックボックステスト**のケースを導く
   - 事前条件: 違反時に例外になるか（境界値を含む）
   - 事後条件: 戻り値が保証どおりか（**最重要**）
   - 不変条件: 操作の前後で保ち続けるか
2. テストの書き方はプロジェクトのテスト規約に従う。**既定**: 契約表の各行を1ケース以上のテストにする
3. テストを先に書き、通るようにプロダクションコードを実装する
4. 純粋な部分は単体テスト（モック不要）、副作用を持つ部分は薄いので結合テストなどで確認する

## 設計チェックリスト

- [ ] 契約表（事前・事後・不変・副作用）を作った
- [ ] 引数・戻り値にプリミティブ型が出ていない
- [ ] 値で検証できない条件はガード節にある
- [ ] 「計算」を名乗るメソッドに DB 保存・送信・ログが紛れていない
- [ ] 副作用を持つメソッドは動詞名で、薄いクラスに閉じ込めてある
- [ ] 純粋ロジックの中で現在時刻・乱数を直接取得していない
- [ ] 値オブジェクトは不変で、変更は新インスタンスを返す
- [ ] 契約表の各行に対応するテストケースがある

## 出力フォーマット

設計の提示では次の順で出す。

1. 責務と配置
2. 純粋部分と副作用部分の一覧
3. 契約表
4. クラス骨子（シグネチャ、値オブジェクト、ガード節）
5. テストケース一覧
