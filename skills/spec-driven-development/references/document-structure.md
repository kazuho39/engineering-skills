# ドキュメント構成の定義（読みやすい specification / design の構成）

specification / design は、1ファイルに全部を書くと数百行になり、読みたい情報にたどり着けない。このスキルでは、**入口の文書を短く保ち、詳細は役割ごとに別ファイルへ分ける**。ここでは、そのファイル構成と各ファイルの書き方を定める。

## 1. 基本方針

1. **入口は1画面で全体像が分かる。** `specification.md` / `design.md` の冒頭に要約と「変更の有無」の表を置き、詳細は見出し・ファイルへのリンクで辿らせる。
2. **主な読み手（実装者）が読むのは、クラス設計とテスト設計。** この2つを独立したファイルにし、入口から1回で辿れるようにする。
3. **根拠と未確定事項は本編から分ける。** ADR（なぜその方式か）と、オープンクエスチョン（未確定事項）は別ファイルにする。
4. **どの文書のものかをファイル名で示す。** ADR やオープンクエスチョンは specification と design の両方で発生しうる。
5. **同じ情報を複数箇所に書かない。** 各情報の置き場所を1つに決める（「5. 情報の置き場所」）。
6. **該当がないものは書かない。** 空の章や空のファイルは作らない。

## 2. ファイル構成

```text
specs/YYYY-MM-DD_<feature-name>/
├── specification.md                 要件（What）の入口＋本編
├── specification-adr.md             要件側の意思決定（あれば）
├── specification-open-questions.md  要件側の未確定事項（あれば）
├── design.md                        技術設計（How）の入口＋本編
├── design-class-design.md           クラス設計（ファイルツリー＋ファイル別見出し）
├── design-test-plan.md              テスト設計（ファイルツリー＋ファイル別見出し）
├── design-adr.md                    設計側の意思決定
├── design-open-questions.md         設計側の未確定事項
└── dig-log.md                       dig スキルによる質問の記録（dig を使った場合のみ）
```

### 命名規則

`<親文書>-<種別>.md`。親文書は `specification` または `design`、種別は下表のとおり。

| 種別 | ファイル | 作成条件 | 主な読み手 |
|------|---------|---------|-----------|
| class-design | `design-class-design.md` | 新規または変更するクラスがあるとき（通常は常に） | 実装者・レビュアー |
| test-plan | `design-test-plan.md` | テストを書くとき（通常は常に） | 実装者・QA |
| adr | `<親文書>-adr.md` | 方式の選択があり、代替案を比較したとき | 設計レビュー・後から見返す人 |
| open-questions | `<親文書>-open-questions.md` | 未確定事項・PoC が必要な箇所・決定済み事項の記録があるとき | 設計レビュー・実装者 |

- **該当がなければファイルを作らない。** 例: 要件側に意思決定も未確定事項もなければ、`specification-adr.md` / `specification-open-questions.md` は作らない。
- 入口の文書に「あるファイル」のリンクだけを置き、「ないファイル」には触れない。
- 親文書の違いに迷ったら、「要件（何を・なぜ・誰が）の判断か」「技術（どう作るか）の判断か」で分ける。両方にまたがる決定は、決定の起点の側に書き、もう一方からはリンクで参照する。

## 3. 入口の文書の構成

### design.md

```markdown
# design（技術設計）: <機能名>

対応する specification / 議論の記録（dig-log）へのリンク

## 開発概要（要約）
  何を作るか（1〜2文）

  ### 変更の有無（あるものは詳細へ）   ← 必須の表
  主な設計判断（3〜5件、各1行。理由は adr へ）

  ### まず読むファイル                  ← 必須の表（知りたいこと → ファイル）

## 1. アーキテクチャ概要
## 2. API設計
## 3. データモデル設計
## 4. 画面設計
## 5. 主要フローの詳細設計              ← シーケンス図とエッジケース
## 6. エラーハンドリング設計
## 7. セキュリティ設計
## 8. パフォーマンス設計
## 9. 実装方針の選定（ADR）            ← 結論の表＋ design-adr.md へのリンク
## 10. 影響範囲
## 11. 移行 / リリース方針
## 12. オープンクエスチョン            ← 件数サマリ＋ design-open-questions.md へのリンク
## テスト設計                          ← 要約＋ design-test-plan.md へのリンク
## 変更履歴                            ← 末尾に残す
```

#### 「変更の有無」表（必須）

実装者とレビュアーが最初に知りたいのは、大きな変更があるかどうか。次の項目を**固定**で並べ、「あり／なし」を必ず明示する。**「なし」の行も残し、理由を1行書く。「あり」の行は、該当する見出しまたはファイルへのリンクを必ず付ける。**

| 項目 | 書くこと | 詳細へのリンク先 |
|------|---------|----------------|
| 新規 API | あり／なし。ありなら本数と主なパス | 「2. API設計」のエンドポイント一覧 |
| 既存 API の定義変更 | あり／なし。ありなら、どの API のどの項目か（互換性の有無） | 「2. API設計」の該当箇所 |
| DB マイグレーション | あり／なし。ありならテーブル・カラムの増減 | 「3. データモデル設計」 |
| 認証・認可 | 変更の有無。新規ルートの認証方式 | 「2. API設計」の認証・認可方式 |
| 画面（フロントエンド） | あり／なし。新規・変更の画面数 | 「4. 画面設計」 |
| 新規クラス | あり／なし。層ごとの数 | `design-class-design.md` のファイルツリー |
| 既存クラスの変更 | あり／なし。ファイル数と主な対象 | `design-class-design.md` のファイルツリー（✎の行） |
| 影響範囲・リリース | 大きさ（小／中／大）と一言 | 「10. 影響範囲」「11. 移行 / リリース方針」 |

案件に応じて行を足してよい（例: 外部サービス連携、設定・環境変数、バッチ）。ただし、上の固定項目は削らない。

#### 「まず読むファイル」表（必須）

| 知りたいこと | ファイル |
|-------------|---------|
| どのクラスを作り、各クラスが何を保証するか | `design-class-design.md` |
| どのテストを書き、どのクラス・受け入れ条件に対応するか | `design-test-plan.md` |
| API・データ・画面・フロー・影響範囲 | `design.md` の本編 |
| なぜその方式にしたか | `design-adr.md`（あれば） |
| 未確定事項 | `design-open-questions.md`（あれば。未解決の件数も添える） |

### specification.md

```markdown
# specification（要件定義）: <機能名>

対応する design / 議論の記録（dig-log）へのリンク

## 要約
  何を・誰のために・なぜ（2〜3文）。スコープ内の主な項目、受け入れ条件の件数

  ### まず読むファイル                  ← あるファイルだけ（adr / open-questions）

## 1. 背景 … 9. 受け入れ条件
## 変更履歴
```

要件側の意思決定（スコープをなぜそう切ったか、仕様の選択肢の比較）は `specification-adr.md`、要件側の未確定事項は `specification-open-questions.md` に置く。specification の「リスク / 懸念点」のうち、未確定事項に当たるものはオープンクエスチョンに移し、本編にはリンクだけを残してよい。

## 4. 分離したファイルの構成

### design-class-design.md（クラス設計）

**ファイルツリーで全体を示し、ファイルごとの見出しで詳細を書く。**

1. **作るクラス（ファイルツリー）**: 凡例（★新規／✎既存を修正／無印は既存）、各行に一言の役割と区分（純粋／DB読み取り／書き込み）。依存の向きを1行添える。
2. **層ごとのセクション**（Domain / Infrastructure / Application / Http など）: **ファイル（クラス）ごとに見出しを立てる**。各見出しに「役割」「区分」と、メソッドごとの表（事前条件・事後条件・不変条件・副作用）を書く。処理の流れが複雑な UseCase などには、見出しの中に疑似コードを置く。
3. **テスト設計へのリンク**。

- 見出し名はファイルツリーのファイル名と一致させる（`### Domain/Product/Entity/Product.php ✎`）。
- 純粋部分と副作用部分の仕分けは、独立した表にせず、ツリーの「区分」と各見出しの「区分」で表す。
- クラスを持たない設計（スクリプトなど）では、このファイルを作らず、design.md の本編に処理の流れを書く。

テンプレート: [design-class-design-template](design-class-design-template.md)

### design-test-plan.md（テスト設計）

**クラス設計と同じ形（ファイルツリー＋ファイルごとの見出し）で書き、クラス設計の各クラスと対応付ける。**

1. **作るテスト（ファイルツリー）**: テストファイルごとに★／✎と「対象: どのクラスか」を書く。
2. **Unit**: テストファイルごとに見出しを立て、「対象」（クラス設計のどのクラスか）とケース表（ケース・期待）を書く。
3. **Feature（結合）**: テストファイルごとに見出しを立て、「対象」（貫通するクラス）と「対応する受け入れ条件」、「観点／主なAC／検証するクラスの契約」の表を書く。
4. **フロントエンドなど、クラス設計の対象外のテスト**: 対応する受け入れ条件を書く。
5. **クラスからテストへの対応確認**: クラス設計の全クラスを行にした逆引き表（Unit／Feature の AC）。**導けない行があれば、その契約が曖昧**なので、クラス設計を直す。

テンプレート: [design-test-plan-template](design-test-plan-template.md)

### \<親文書\>-adr.md（意思決定の記録）

- 先頭に「ADR 一覧」（決定・主な理由）を置き、入口の文書の「実装方針の選定」節にも同じ表（結論のみ）を置く。
- ADR ごとに「推奨案」「代替案との比較表」「採用理由」「トレードオフ」。末尾に「前提条件」と「再検討トリガー」をまとめる。
- 起点が別の文書にまたがる決定は、「関連: specification の AC-xxx に反映済み」のように相互参照する。

テンプレート: [adr-template](adr-template.md)

### \<親文書\>-open-questions.md（未確定事項）

次の3区分で書く。

- 決定済みの事項（参考）: レビューなどで決まったこと。経緯を残す
- 実装・検証しながら確かめる事項（チェックボックス）
- PoC が必要な箇所

入口の文書の「オープンクエスチョン」節には、未解決の件数と PoC の有無だけを書く。

テンプレート: [open-questions-template](open-questions-template.md)

## 5. 情報の置き場所（重複させない）

| 情報 | 置き場所 | 他の場所では |
|------|---------|-------------|
| 作る・変更するクラスの一覧 | `design-class-design.md` のファイルツリー | design.md の「影響範囲」は件数だけ書く |
| クラスの契約（事前・事後・不変条件） | `design-class-design.md` の各見出し | 他は参照のみ |
| 作るテストの一覧とケース | `design-test-plan.md` | design.md は件数と対象 AC の範囲だけ |
| 受け入れ条件と、それを検証するテストの対応 | `design-test-plan.md` の対応確認表 | specification は AC を定義するのみ |
| 方式の比較・採用理由・再検討トリガー | `<親文書>-adr.md` | 入口の文書は結論の表だけ |
| 未確定事項・決定済みの経緯 | `<親文書>-open-questions.md` | 入口の文書は件数だけ |
| API の仕様・データモデル・画面 | design.md の本編 | 他は参照のみ |
| 変更の経緯 | 各親文書の末尾の「変更履歴」 | 本文に「レビューで決定」などの経緯を混ぜない |

## 6. 書き方のルール

- **該当しない章は省略するか、1行で済ませる。** 「対象外」「使用しない」とだけ書く章は、テンプレートに残っていても削ってよい（「変更の有無」表の固定項目は除く）。
- **リンクは相対パスと見出しで張る。** 見出しを変えたら、リンク元も直す。
- **入口の文書には、詳細を書かず、結論とリンクだけを書く。**
- **用語は一度定義したら、ファイルをまたいでも同じ名前を使う。**
- **生きたドキュメントとして更新する。** 実装中に判明した変更は、置き場所の表に従って該当ファイルを更新し、親文書の「変更履歴」に経緯を残す。

## 7. 後続の工程から見たときの読み順

| 工程 | 読むもの |
|------|---------|
| 実装（developer） | design.md の入口 → `design-class-design.md` → `design-test-plan.md` → 必要に応じて本編（API・画面など） |
| レビュー | design.md の入口の「変更の有無」→ クラス設計とテスト設計 → ADR |
| QA | `design-test-plan.md` → specification の受け入れ条件 |
