# Design Template（技術設計テンプレート）

`design.md`（入口＋本編）を作るときは、以下をベースに整理してください。

**ファイル構成**: design は1ファイルに全部を書かず、役割ごとに分ける。入口の `design.md` には要約・「変更の有無」表・API/データ/画面/フローなどの本編を書き、クラス設計・テスト設計・ADR・未確定事項は別ファイルにする。構成の定義: [document-structure](document-structure.md)。

| 分離するもの | ファイル | テンプレート |
|-------------|---------|-------------|
| クラス設計（ファイルツリー＋ファイル別見出し） | `design-class-design.md` | [design-class-design-template](design-class-design-template.md) |
| テスト設計（ファイルツリー＋ファイル別見出し） | `design-test-plan.md` | [design-test-plan-template](design-test-plan-template.md) |
| 実装方針の選定（ADR） | `design-adr.md` | [adr-template](adr-template.md) |
| オープンクエスチョン | `design-open-questions.md` | [open-questions-template](open-questions-template.md) |

## 📌 記入例（全体の流れをつかむため、先に読んでください）

## 冒頭: 開発概要（要約）

`design.md` の先頭（タイトルと、specification・dig-log へのリンクの直後）に置く。**1画面で全体像と変更の有無が分かる**ようにする。

```markdown
## 開発概要（要約）

**何を作るか**: {1〜2文。誰が何をできるようになるか。何を再利用し、何を新設するか}

### 変更の有無（あるものは詳細へ）

| 項目 | 有無 | 内容 | 詳細 |
|------|:----:|------|------|
| 新規 API | **あり**／なし | {本数と主なパス・認証} | [エンドポイント一覧](#エンドポイント一覧) |
| 既存 API の定義変更 | あり／**なし** | {ありなら、どの API のどの項目か。互換性は保たれるか。なしなら理由を1行} | [{該当見出し}](#…) |
| DB マイグレーション | あり／**なし** | {テーブル・カラムの増減。なしなら「スキーマ変更なし」} | [データモデル設計](#3-データモデル設計) |
| 認証・認可 | {変更あり／新規ルートのみ／なし} | {方式の要点} | [認証・認可方式](#認証認可方式) |
| 画面（フロントエンド） | **あり**／なし | {新規・変更の画面数} | [画面設計](#4-画面設計フロントエンド) |
| 新規クラス | **あり**／なし | {層ごとの数} | [作るクラス](./design-class-design.md) |
| 既存クラスの変更 | **あり**／なし | {ファイル数と主な対象} | [作るクラス（✎ の行）](./design-class-design.md) |
| 影響範囲・リリース | 小／中／大 | {一言} | [影響範囲](#10-影響範囲)、[リリース方針](#11-移行--リリース方針) |

規模: 新規 約{N}ファイル（テスト含む）、既存修正 約{M}ファイル。

**主な設計判断**（理由と代替案は [design-adr.md](./design-adr.md)）:

1. {判断1}
2. {判断2}

### まず読むファイル

| 知りたいこと | ファイル |
|-------------|---------|
| どのクラスを作り、各クラスが何を保証するか | [design-class-design.md](./design-class-design.md) |
| どのテストを書き、どのクラス・ACに対応するか | [design-test-plan.md](./design-test-plan.md) |
| API・データ・画面・フロー・エラー・セキュリティ・影響範囲 | 本書（以下の1〜11章） |
| なぜその方式にしたか | [design-adr.md](./design-adr.md) |
| 未確定事項 | [design-open-questions.md](./design-open-questions.md)（未解決 {N} 件） |
```

- 「変更の有無」表の項目は**固定**。「なし」の行も残して理由を1行書き、「あり」の行は詳細へのリンクを必ず付ける。項目は案件に応じて足してよいが、固定項目は削らない（[document-structure](document-structure.md) の「変更の有無」表）。
- 該当しないファイル（例: ADR を作らなかった）は「まず読むファイル」表に載せない。

  - 例: データベースロールバックスクリプト準備
- {影響の有無}
  - 例: 既存機能への影響なし（新規機能）
  - 例: データ整合性に注意が必要

### フィーチャーフラグの使用

```text
if ({feature_flag_check}) {
    // 新機能
} else {
    // 旧機能（or なし）
}
```
